# V1.3 Phase 3B: independent safety checks; installation blocked

Work started on `feature/v1.3-balanced` at
`0d7c495cb4fca5c8467af29de2898474477473f5`. Branch and HEAD matched the
requested baseline; the tracked tree was clean. The four untracked V1.2 reports
were preserved and excluded. No previous history was rewritten.

**This is a partial milestone, not a completed in-app installation workflow or
an RC1 release-readiness claim.** The requested stop condition applies: a
consistent application-wide persistence handoff and a demonstrably safe Windows
process-lifetime/installer helper have not been established. Installation stays
disconnected, including for signed test packages. No Install button, consent
dialog, shutdown, raw profile copy, installer execution, relaunch, or rollback
has been added. The existing Blue Thread download/verify/ready presentation and
manual GitHub fallback remain.

## Implemented and connected: registered installation evidence

`electron/update-installation.ts` replaces the marker-only download-eligibility
probe in main IPC. It requires all of:

- Packaged Windows x64, `win-nsis`, and an executable named `Planstrand.exe`.
- The current user's registration at the electron-builder-derived product GUID
  `f742ac0b-6794-588a-a5f8-d13e36ad8eb9`, with `InstallLocation` matching the
  running executable's directory and the exact quoted uninstaller command with
  `/currentuser`.
- Consistent current-user registry views and no machine-wide registration or
  orphan machine-wide uninstall command in either view. The relevant HKCU
  Software keys are shared across WOW64 views; identical reads are expected.
  See Microsoft's [registry view rules](https://learn.microsoft.com/en-us/windows/win32/winprog64/shared-registry-keys).
- A local, canonical drive path, ordinary nonempty executable/uninstaller files,
  and the exact Planstrand ownership marker. Missing/inaccessible evidence,
  installation/ancestor links, alias paths, repository ancestors, UNC/device
  paths, ambiguous paths, foreign markers and conflicting registrations deny.

The bounded read-only registry program uses system Windows PowerShell with no
profile, a hidden window, fixed registry keys, a ten-second timeout and bounded
UTF-8 JSON output. No renderer data enters its command or arguments. Failures
produce an opaque unavailable result, never registry diagnostics or paths.
PowerShell unavailable or blocked by policy means manual fallback. Registrations
are read, never created or modified. Custom installation directories are accepted
when they match the registration; profile paths are not consulted or inferred.

This is local installation evidence at probe time. It neither authenticates the
publisher nor locks the installation against concurrent changes. Existing NSIS
destination/tree ownership and reparse-point protections remain unchanged and
would still be required at execution. No assertion is made that this Node probe
duplicates every native NSIS reparse-point check.

## Implemented and tested, not connected to execution: staged revalidation

`UpdateDownloadService.revalidateStagedDownload()` accepts no arguments and
returns only the existing path-free status. Main retains private copies of the
authenticated manifest/signature from the successful Phase 3A download, and
snapshots its configured public-key map. Revalidation:

1. Requires a successful process-owned download and a fresh eligibility probe.
2. Verifies the retained Ed25519 signature, release identity, exact Setup filename,
   platform/package/architecture and successor/channel policy again.
3. Requires the expected attempt directory under the main-owned staging root,
   canonical paths, a non-symlink regular file with one link and the signed size.
4. Hashes the opened file again, bounds its bytes, checks readback size/hash and
   checks metadata before/after reading. Reports Verifying while the check is
   pending; concurrent calls cannot report completion prematurely.
5. Clears readiness on failure, without removing unrelated or earlier files.

This method is deliberately **not an execution grant** and is not exposed through
IPC. Node's ordinary read handle does not deny Windows write/delete sharing.
Closing that handle and later spawning its pathname leaves a substitution window.
A future helper must hold native deny-write/delete handles for the package and
relevant path components through authentication and process creation; a second
hash followed by ordinary `spawn(path)` is insufficient. No unsafe spawn has
been connected. Only discovery, download and status IPC remain available, with
the existing trusted-window/main-frame/origin checks.

## Exact blockers at the handoff boundary

The blockers are independently reproducible from the existing implementation:

- `UpgradeCheckpointService.prepare()` holds the operation-log lock only during
  model capture, then releases it before writing the checkpoint. It establishes
  a point-in-time application-data checkpoint, not a permanent mutation barrier.
- `OperationWriteFlushService` drains captured operations, not every persistence
  producer. `PluginUserPersistenceService` has timer-coalesced data and asynchronous
  compression/commit chains that may not yet have dispatched an operation.
- Plugin secret and OAuth stores use separate direct IndexedDB transactions;
  `core/persistence/local-storage.ts` writes directly to localStorage. Electron
  `simple-store.ts` has a private asynchronous save queue without an updater
  freeze/drain contract. Stopping reducer updates alone would not drain these
  stores and could discard accepted pending plugin changes.
- The existing close flow can sync or finish the day, generating further writes.
  `start-app.ts` also has a two-second forced-exit fallback after windows close.
  Neither a window-close event nor that timer confirms durable completion or
  termination of all Electron/storage/utility processes.
- There is no independent helper that owns kernel process identities/handles,
  prevents profile reopening while it copies, verifies the complete closed copy,
  and retains package/path locks through installer creation. PID-only polling,
  renderer acknowledgements, arbitrary waits, or a live LevelDB copy would not
  satisfy this boundary.

Therefore `prepare()` was not wired to installation. Failure/success of a model
checkpoint cannot authorize shutdown or installation in this revision. This
avoids adding a partial freeze that appears safe while losing pending changes.
These are implementation blockers, not a request for signing credentials or
owner permission to bypass the requirements.

## Recovery coverage and instructions

No full-profile recovery point is produced by these changes. Phase 2's existing
verified application-data JSON checkpoints remain unchanged, including their
archive/model coverage and their exclusions. They are not full filesystem copies.
Existing application-data import tests from Phase 2 do not prove raw profile
restoration, credential preservation, or a packaged upgrade/restart.

For a checkpoint already produced by the existing service, keep the verified file
private and use Planstrand's existing complete-backup import path in a disposable
`--user-data-dir=<absolute-test-path>` profile first. Import replaces supported
models and creates a new client identity; it does not restore every device-local
setting, operation history, sync credential or plugin secret. Do not import into
the real profile as a rehearsal.

A future full-profile copy must capture the **resolved** `app.getPath('userData')`,
normally `%APPDATA%\Planstrand`, and must pass that exact absolute path through
relaunch. Never substitute the default when a custom profile was selected. The
helper and unique recovery destination must be outside both installation and
source profile, reject unsafe/reparse destinations and recursion, check available
space and every copy failure, verify all supported files by readback before
publishing a recovery marker, and leave all previous verified points intact.
Coverage must include IndexedDB (including credentials/plugin databases),
localStorage, Chromium preferences and device-local configuration. Reopening
must be blocked until copying ends. An incomplete attempt must not launch NSIS.

Manual full-profile recovery is **not implemented or rehearsed here**. A future
procedure must close all relevant processes, retain the failed profile separately,
verify the chosen recovery manifest, restore to the original resolved path without
merging stores, and verify model/credential access with a compatible installed
version before reconnecting sync. No automatic rollback should be inferred.
External encryption keys, Windows account/device-bound decryption material and
separately configured sync storage remain outside even a complete profile copy;
preserve keys separately and expect reauthentication where necessary. A copy on
the same disk is not independent protection from disk loss.

## Production trust gate and remaining RC1 work

`UPDATE_PUBLIC_KEYS` is still empty. No production identity was invented or
authorized; disposable signing keys exist only in tests, and no private key or
test trust root is embedded in builds. Historical unsigned releases remain manual.

The owner must authorize a stable Ed25519 key ID, private-key custody, and the
public SPKI PEM/fingerprint through an independently verified owner-controlled
channel. Only the reviewed public key may be embedded in `update-trust.ts`; keep
private material outside the repository/application/chat/logs. First distribute a
build containing that authorized key through the manual Setup path. Sign and
verify exact reviewed future artifacts using the Phase 3A tool, then extend the
existing protected release preparation/upload verification to include the detached
manifest and signature without replacing historical assets. **Provisioning a key
alone must not enable installation while the handoff blockers remain.**

Before RC1 can claim assisted installation:

1. Establish a tested stop/drain/resume contract covering accepted mutations,
   queued plugins, sync, independent stores and native settings. Call Phase 2
   `prepare()` only after stopping new mutations; retain the barrier until clean
   exit and release it safely on preparation failure.
2. Implement/review the independent Windows helper, whole-process termination
   proof, profile reopening exclusion, full-profile copy/verification/retention,
   storage failures, native package/path locks and validated registered destination.
3. Add explicit consent and the small Blue Thread Install/confirmation/preparation
   states only when all prerequisites are available. No silent installation.
4. Validate NSIS cancellation/failure, preserve recovery points, confirm installed
   version/destination before relaunch, and pass the exact custom profile override.
5. Complete both packaged rehearsals and manual recovery with disposable Windows
   registrations/profiles. Confirm Tasks, Folders, Planning, WorkSessions, Events,
   recurring series, Weekly Templates, archives and settings after restart.
