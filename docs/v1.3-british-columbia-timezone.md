# V1.3 British Columbia timezone compatibility

Investigated on `feature/v1.3-balanced`, baseline `1d3b88b`, October 14, 2026.
Windows, application data, sync formats and existing testing artifacts were preserved.

## Root cause established before implementation

The installed runtime is Electron **43.5.0**, Chromium **150.0.7871.250**, ICU
**78.2**, timezone data **2025c**. There are two independent failures:

1. Its Windows-to-IANA mapping cannot resolve `British Columbia Standard Time`.
   Both main and sandboxed renderer return an undefined default Intl timezone
   and a constant GMT-08:00 local Date. The read-only registry query reports the
   legitimate new ID, base Bias 480 and current ActiveTimeBias 420. At
   `2026-10-14T07:00:00Z`, native Date therefore says October 13, 23:00. Its
   midnight arrives an hour after Vancouver's midnight.
2. Explicit `America/Vancouver` uses the bundled 2025c rules. It correctly uses
   UTC-07:00 in October, but incorrectly falls back at `2026-11-01T09:00:00Z`.
   Mapping the Windows ID alone would leave November and winter scheduling wrong.

Microsoft documents the new Windows zone in its
[BC guidance](https://techcommunity.microsoft.com/blog/dstblog/interim-guidance-for-british-columbia-time-zone-changes-2026/4544988).
Unicode's [Windows lookup implementation](https://chromium.googlesource.com/chromium/deps/icu/+/ca4689c/source/common/wintz.cpp)
uses the Windows identity to look up bundled `windowsZones` data.
[IANA tzdb 2026b](https://www.iana.org/time-zones/releases/2026b) introduces the
permanent Vancouver rules. The latest released ICU tzdata resource set, 2026e,
was also inspected: its `windowsZones.res` still lacks the new Windows ID.

## Existing application paths

- `electron/system-time-zone.ts` already maps this exact Windows identity to
  `America/Vancouver` when default Intl resolution fails. `main-window.ts`
  passes it through the sandboxed preload bridge. This helped explicit IANA
  editors, but did not repair JavaScript's default timezone or update its rules.
- `getDbDateStr` reads native Date year/month/day. `DateService.todayStr` and
  `CurrentDateService.today` use it. CurrentDateService schedules native civil
  midnight with `setHours(24, 0, 0, 0)`, with hourly, focus, visibility and native
  resume recovery. Its timer was correct for the runtime's incorrect local zone.
- Today and Planning use that clock. Plan Today/Tomorrow resolve the current
  date at intent time; This Week derives civil week keys from it. Native Date
  also participates in task scheduling and date pickers.
- `iana-time-zone.ts` resolves explicitly configured zones before the system
  fallback and converts editor wall times through Intl. Calendar uses that
  resolver and a zone-specific date derived from the shared reactive clock.
- Local Event/WorkSession reminders subtract their preference offset from the
  stored start epoch. The worker supplies ten-second ticks, and `checkDue`
  compares epochs with Date.now. Their due comparison needs no timezone change;
  the creation of those epochs and their display needed consistent rules.

## Smallest complete fix

1. Initialize the process-local `TZ` to the existing native IANA fallback as the
   first main-process import, only on Windows when TZ is unset/empty and native
   Intl cannot resolve the system zone. Node refreshes its ICU/V8 default, and
   child renderers inherit it. Recognized native zones and nonempty explicit TZ
   values are left alone. No machine/user environment variable is written.
2. Refresh Electron's four timezone resources to the unmodified official
   **2026b** data during Windows `electron:build` and Windows `afterPack`.
   This is the earliest release containing the required rules, adding 235,936
   bytes of build inputs. Electron and npm dependency versions stay unchanged.
   Source commit, SHA-256 checksums and redistribution license are recorded.
   Builds and application startup do not download anything.

ICU explicitly supports [replacing timezone resources in its .dat package](https://unicode-org.github.io/icu/userguide/datetime/timezone/#icu4c-tz-update-of-a-dat-package-file).
The build helper implements the little-endian ICU package relocation using Node
buffers, so a native icupkg build dependency is unnecessary. It validates the
format, resource offsets and source checksums, writes atomically, and does not
downgrade equal/newer tzdb. Packaging errors fail the build. Main, renderer,
preload and worker then consume the same data file.

The real 2,361-resource package was compared before and after: all unrelated
resource bytes and names were identical. Only `timezoneTypes.res` and
`zoneinfo64.res` actually changed; the other two official resources were already
byte-identical. The package grew by 400 bytes.

Rejected alternatives were verified in disposable Electron processes:

- Process TZ alone fixes October but retains the incorrect November fallback.
- Setting `ICU_TIMEZONE_FILES_DIR` inside main is too late. Supplying it before
  launch updates main-process Intl, while the sandboxed renderer still uses its
  bundled data. It does not give consistent application behavior.
- The Chromium test timezone switch did not change this runtime's result.
- Fixed offsets, substituting another city's zone, or patching Date/Intl would
  undermine historical rules or require substantially broader application changes.

No entity, reducer, schema, migration, sync payload or persisted timestamp was
changed. Configured Event/WorkSession and Calendar zones retain their identities.
Today remains system-local; Calendar can intentionally use its configured zone.
Previously saved erroneous instants are preserved and require an intentional
user edit if correction is desired. While the BC startup fallback is active,
restart the application after changing the OS timezone so all child processes
inherit the new setting. No OS setting was changed during this investigation.

## Focused validation

| Check                                                                                      | Result    |
| ------------------------------------------------------------------------------------------ | --------- |
| Resolver/startup unit tests                                                                | 12 passed |
| ICU replacement and isolated Windows afterPack hook tests                                  | 4 passed  |
| Opt-in native Electron main/renderer/worker regressions                                    | 2 passed  |
| Seven focused Angular files                                                                | 87 passed |
| Electron TypeScript compilation, changed TypeScript ESLint, Prettier and whitespace checks | Passed    |

Native regressions use the actual BC Windows zone, without a CDP timezone
override. They cover historical winter/summer and the November 2025 fallback,
the March 2026 transition, October midnight, November 1 remaining UTC-07:00,
December 2026, January 2027 and January 2030. Date and explicit Vancouver Intl
agree in all three contexts. Explicit `TZ=Asia/Tokyo` is preserved, and explicit
Vancouver formatting still uses the corrected rules.

Planstrand D was separately exercised through its real application entry point
against a local dev server with fresh disposable profiles and renderer-only test
clocks. Its real timers rolled Today over at 07:00 UTC in October and November.
Plan Today wrote `2026-10-14`, Tomorrow wrote `2026-10-15`, and This Week wrote
`2026-10-12` (October 12–18). Calendar's current-date highlight agreed.
November 1 09:00 Event creation stored `16:00Z`; 09:30 WorkSession scheduling
stored `16:30Z`. After reopening the same disposable profile, those epochs were
unchanged. Reminder eligibility counts at `15:59:59Z`, `16:00Z`, `16:29:59Z`
and `16:30Z` were respectively **0, 1, 1, 2**, with no replay on another check.
Notification delivery was stubbed for this eligibility test; Windows toast
visibility remains a manual check.

Local evidence, probe scripts, JSON results, the original development ICU file
and a November Calendar screenshot are retained under
`.tmp/bc-timezone-20261014/`. Earlier profiles/builds were not overwritten.
No Setup/Portable EXE or other distribution was built. No publishing, pushing,
merging or tagging was performed. Only focused tests were run. The commit uses
the completed changed-file lint/format checks instead of the standard hook:
`npm run lint` also runs unrelated lint-rule, tool and macOS-icon test suites.
The hook configuration itself is unchanged.

Reproduce the focused native checks after `npm run electron:build` on a machine
already using the BC Windows timezone (do not change the OS to run them):

```powershell
node --test electron/system-time-zone.test.cjs tools/update-electron-timezone-data.test.cjs
$env:PLANSTRAND_TEST_ELECTRON_TIMEZONE = '1'
node --test electron/bc-time-zone-runtime.test.cjs
```

The seven Angular includes were `current-date.service.spec.ts`,
`iana-time-zone.spec.ts`, `pages/planstrand/planstrand.spec.ts`,
`calendar-display.service.spec.ts`, `local-schedule-reminder.service.spec.ts`,
`dialog-event.component.spec.ts` and `work-session.service.spec.ts`, run with
`TZ=Europe/Berlin`, `--watch=false --no-code-coverage --source-map=false`.

## Manual verification using Planstrand D

1. From the repository root, start `npm run startFrontend`. In a second terminal
   create a new profile path and launch the updated development app:

   ```powershell
   $bcProfile = Join-Path $PWD ('.tmp\bc-manual-' + [DateTimeOffset]::UtcNow.ToUnixTimeMilliseconds())
   npm start -- "--user-data-dir=$bcProfile"
   ```

   This builds the Electron JavaScript and refreshes the development ICU data,
   then opens **Planstrand D**. Restart an older running instance to load the
   updated resources. Keep Windows timezone/security settings unchanged.

2. In its Developer Tools, confirm
   `Intl.DateTimeFormat().resolvedOptions().timeZone` is `America/Vancouver`.
   Inspect these instants with `new Date(iso).toString()` and
   `new Date(iso).getTimezoneOffset()`:

   | ISO instant            | Expected local time | Offset minutes |
   | ---------------------- | ------------------- | -------------- |
   | `2026-01-15T08:00:00Z` | January 15 00:00    | 480            |
   | `2026-10-14T06:59:59Z` | October 13 23:59:59 | 420            |
   | `2026-10-14T07:00:00Z` | October 14 00:00    | 420            |
   | `2026-11-01T09:00:00Z` | November 1 02:00    | 420            |
   | `2027-01-15T07:00:00Z` | January 15 00:00    | 420            |

   ICU may still label permanent time "Pacific Daylight Time"; verify the fields
   and offset rather than the display name.

3. Create Tasks in the disposable profile. Use Plan Today, Plan Tomorrow and
   Move to This Week; verify their Planning dates and the Calendar current-date
   highlight. At local midnight, Today should advance immediately. Repeat after
   minimizing/restoring or sleeping/resuming across midnight.
4. Create an Event on November 1, 2026, 09:00–10:00 in America/Vancouver and a
   WorkSession at 09:30. Reopen them to confirm their wall times. An Event with
   an explicit Asia/Tokyo zone should retain that zone and its own wall time.
5. For actual toast delivery, create a new Event a few minutes ahead with
   "when it starts", then repeat with a WorkSession reminder. Allow ten seconds
   for the worker tick. Repeat minimized, then reload and check no duplicate
   toast. Keep Disable all reminders off. Use a new start instant for retries.
