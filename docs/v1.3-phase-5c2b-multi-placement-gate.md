# V1.3 Phase 5C.2B: multi-placement implementation gate

## Decision

**Defer independent multi-placement Planning to V1.4. No persisted-contract or UI
implementation is shipped by this phase. This result does not qualify a
multi-placement candidate for packaged upgrade testing.**

The blocker is the transition from a Task-scoped replacement register to
independent membership registers, including the still-valid operations outside a
snapshot. A record-shape migration alone cannot preserve the meaning of those
operations. A safe implementation needs either a second bounded materialization
and durable cutover protocol, or an explicitly specified, retained V1 register
and cutover-evidence model. Neither exists for schema-5 Planning today.

This is an implementation-scope judgment, not a claim that multi-placement is
impossible. Extending the startup, synchronization, checkpoint recovery and
backup paths together is disproportionate to a focused change during V1.3 RC
acceptance. The user explicitly authorized stopping persisted implementation at
this gate when safe migration/replay requires a disproportionately large rewrite.

## Precise cutover failures to avoid

### Snapshot followed by a legacy move

1. A schema-5 snapshot contains Task X planned on October 5, revision 7.
2. A valid unsnapshotted `PLANNING_V1` Set contains X on October 6, revision 8.
3. Migrating the snapshot to membership `(X, DAY, October 5)` and independently
   translating the tail Set to `(X, DAY, October 6)` leaves two memberships.

The correct V1 result is October 6 only. The old Set is a replacement, not an Add.
Its payload does not identify the old destination. The same issue occurs with a
WEEK-to-DAY or DAY-to-WEEK replacement.

### Snapshot followed by a legacy tombstone

1. The snapshot has the same October 5 placement.
2. Its tail contains a valid V1 record `{ id: X, placement: null, revision: 8 }`.

That tombstone deliberately has no target. A destination-scoped migration cannot
know which membership to remove from this operation alone. Dropping the tombstone
retains a placement the user removed. Giving it a new arbitrary placement ID does
not invalidate the migrated membership.

### Late legacy replay after a new multi-placement gesture

Suppose V2 has already added an independent October 7 membership. Treating a
historical V1 Set/Remove as a current V2 Move/Unplan Everywhere can erase that new
membership. Treating it as an Add can restore obsolete membership instead.
Rejecting all V1 history immediately loses valid local tails and retained remote
history that has not yet been materialized. A durable boundary must distinguish
source history from new user intent; operation timestamps are insufficient.

### Enumerated removals are insufficient for Move and Unplan Everywhere

If A sees only Monday while B adds Tuesday offline, A's Move to Friday cannot
merely emit Remove(Monday) plus Add(Friday). Tuesday survives when replay arrives.
Independent dispatch also permits a partially captured gesture. A Task-wide
replacement barrier and destination write must be one durable intent. A reorder
must never reactivate membership removed by another operation.

The existing server reader gate is useful and should be reused: it fences reads
and writes using advertised capabilities, including encrypted payload requirements
and retained history. This investigation did **not** find that server capability
fencing itself needs a new hosted service or replacement protocol.

Two viable implementation approaches require further work:

1. Generalize bounded materialization to cover complete V1 state and its source
   tail before installing one V2 checkpoint. Preserve raw source/recovery anchors,
   acknowledgement-before-install behavior, offline startup and retry identity.
2. Retain a separately validated V1 register substrate and durable cutover
   evidence alongside V2. Specify its merge with offline snapshots and legacy
   tails, including exactly when V1 ceases to be authoritative. Do not discard
   this evidence during compaction or import.

Neither approach may silently drop V1 history or reinterpret historical V1
operations as new multi-placement gestures. Selecting and proving one across
local hydration, file snapshots, server reconstruction and backup recovery is
required before the new schema is written.

## Proposed minimal V1.4 contract (not implemented)

Use one canonical Task. Membership identity is the tuple
`(taskId, target.type, target.key)`; DAY and WEEK are distinct destinations even
when their date keys are equal. An unambiguous target ID such as `DAY:2026-10-05`
can be scoped inside a Task record, avoiding wire-ID length issues from appending
arbitrary Task IDs. Each membership retains its immutable target and independent
membership/tombstone and ordering revisions. Reorder updates only order, never
membership. This also prevents a late reorder from resurrecting a removal.

Reuse fractional order keys and the existing total revision comparison. Add a
Task-scoped replacement barrier. Capture Move or Unplan Everywhere as one
validated `PLANNING_V2` intent; Move includes both the barrier and desired live
membership. The barrier suppresses older memberships, including ones first
received later. A membership created at the Move's exact revision is visible;
concurrent gestures resolve by the total revision order. New logical counters
must exceed all observed membership/order/barrier counters for that Task.
Keep tombstones and barriers through snapshot merge, export/import and compaction.

Reserve operation/snapshot schema **6**, a distinct **PLANNING_V2** operation
family and semantic reader capability, and backup cross-model **4.6** for this
proposal. Finalize the versions together with the cutover implementation. Require
the new capability on even empty V2 slices: emptiness does not make a changed
contract safe for an old writer. Update file manifests, full-state inference,
client/server advertisements and recovery admission together. IndexedDB can remain
**12** if its object stores/indexes remain unchanged.

V1.2 migration must still materialize its legacy history and perform the existing
V1 projection first. Then convert the complete V1 result once, preserving each
surviving target/order/revision and all V1 tombstone/cutover evidence. Schema-5
profiles additionally require handling their valid V1 snapshot tails. Re-running
migration or seeing a downgraded label must not reproject stale Planner/due fields.

Older clients must refuse new snapshots, backups and operations before mutation
or cursor advancement. File sync must refuse unknown V2 semantics before fallback
or write. SuperSync must refuse both reads and writes from a client lacking V2,
including after operation compaction. Mixed V1/V2 live planning is not proposed;
legacy operations are source history processed through the explicit cutover.

## Command and UI specification for the deferred implementation

- **Add Task to Date/Week:** retain other destinations; an existing membership is
  a no-op, including its order. A deliberate re-add after removal gets a new
  membership revision.
- **Move Task to Date/Week:** replace all older destinations atomically using the
  Task barrier; use one durable intent, not a loop of independently captured
  removals followed by an add.
- **Remove from this Day/Week:** affect that membership only, including Today
  context actions. **Unplan Everywhere** is separately explicit.
- Preserve Today, Tomorrow, This Week and Next Week quick actions as **Move** to
  retain their existing replacement behavior; label/document them as Move.
  Provide separate Add controls in a compact destination picker.
- Tasks/Inbox/Folders show a compact first destination and additional count, with
  a keyboard-accessible full destination list and individual Remove controls.
  Preserve title, deletion and Folder controls.
- Focus tests today's membership independently of other placements. This Week
  shows each DAY membership in its day and the WEEK membership in Anytime;
  their contextual controls and ordering must identify the relevant destination.
- Resolve local civil dates and configured week starts. No deadlines, reminders,
  Folder ownership, WorkSessions, Calendar Events or Weekly Templates are written
  by Planning gestures. Calendar's timed projections remain separate.

These are proposed semantics, **not changes available in this build**. Current
quick actions and single-placement UI remain as documented in Phase 5C.2A.
