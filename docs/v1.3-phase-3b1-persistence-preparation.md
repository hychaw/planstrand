## Implemented: native simple-settings admission and drain

`prepareSimpleStoreForUpdate({ userConfirmed, signal?, timeoutMs? })` in
`electron/simple-store.ts` is a main-only primitive with explicitly limited
`coverage: 'electron-simple-settings'`. The future caller must obtain actual user
consent; this API checks the supplied confirmation flag, not a displayed dialog.
It is not exposed to the renderer and has no startup/shutdown call site.

- Without `userConfirmed === true`, it returns `CONSENT_REQUIRED` without pausing.
- Before its first await, it closes admission to public store saves **and reads**.
  Reads are included because existing corrupt/legacy-file handling can rename
  files. New calls reject with a fixed error, rather than being silently dropped
  or deferred across an exit.
- It tracks every admitted operation, including queued saves, and awaits their
  actual promise completions. Admitted saves finish their private read/merge/write
  path even after admission closes. Completion includes the existing temporary
  write and rename acknowledgements, not just queue submission.
- Success returns an owned lease with `active` and idempotent `resume()`. New
  store calls remain blocked while the lease is active. Repeated preparation
  returns `BUSY`; an old lease cannot release a later lease.
- Abort during draining returns `CANCELLED`; abort after success invalidates and
  releases that lease. Timeout returns `TIMED_OUT`. The default/max watchdog is
  30 seconds; it is a failure deadline, never evidence that a write completed.
- Failure/cancellation/timeout reopen admission. They do not cancel accepted
  writes: later saves remain ordered behind the existing serial queue. No data
  reset, import, queue purge, repair, retry write or backup is initiated by this
  preparation operation.
- Any observed store persistence failure prevents a successful preparation for
  the rest of that process, even if a later queued save succeeds. This includes
  read failures that the existing normal loader handles by returning `{}`.
  Ordinary reads/writes still work; a new process is required before attempting
  preparation again after addressing the underlying problem. Restart alone is
  not evidence that previously failed user intent became durable.

An already admitted read may finish the existing quarantine/legacy-rename logic;
the primitive waits for it. A corruption/read/rename error cannot become update
preparation success. The operation itself does not open or repair settings files.
The existing writer is unchanged: these acknowledgements are not new fsync,
readback, power-loss, or full-profile guarantees.

**Coverage ends at the store API.** In particular,
`plugin-node-consent-store.ts` has its own `_mutationQueue` around a
read/modify/write. A queued consent command not yet at the store, or one between
its load and save, is not an admitted store operation. Its producer must be stopped
and that outer command drained **before** acquiring this lease. Fire-and-forget
main IPC producers must also handle refused saves. The primitive must not be
wired into an active application as if it covered those producers.

## Implemented: checkpoint refusal during detected import

`UpgradeCheckpointService.prepare()` now refuses a detected import before task
time flushing, rechecks inside the operation-log cutoff, and rechecks after
archive reads. It returns the existing `PREPARATION_FAILED` result and never
writes a native checkpoint for those detected overlaps. It does not modify live
data to make preparation succeed. Once import is no longer active, ordinary
checkpoint preparation remains available.

`ImexViewService.isDataImportInProgress` is an observation, not exclusive
admission. This change does not stop imports or guarantee the flag stays false.
It does not strengthen the existing checkpoint into an application-wide barrier
or raw-profile-copy grant. Existing task-time flush, operation cutoff, model
validation, detached export, and verified native checkpoint semantics remain.

## Actual boundaries relevant to the unresolved barrier

| Work                                       | Completion authority / admission gap                                                                                                                                                                                                | Needed before clean shutdown versus after exit                                                                                                                                                                    |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reducer actions and operation capture      | Captured pending count, operation writer promises and `OPERATION_LOG`; a reducer-only gate does not cover accepted asynchronous commands or direct storage writes                                                                   | Drain accepted operations; do not discard their later dispatches                                                                                                                                                  |
| Snapshots                                  | `OperationLogSnapshotService` uses `flushThenRunExclusive`; its transaction must finish, not just its invocation                                                                                                                    | Await active snapshot/transaction; keep admission closed during handoff                                                                                                                                           |
| Archives                                   | `TASK_ARCHIVE` serializes archive mutations. `moveTasksToArchiveAndFlushArchiveIfDue` already uses `OPERATION_LOG` then `TASK_ARCHIVE` and writes before dispatch. Other local archive side effects queue in a separate `concatMap` | Await whole admitted archive commands/effect queue. An empty capture count or one lock acquisition does not drain work not yet at that lock                                                                       |
| Import/export/backup                       | Import spans async validation, operation persistence, provider sequence resets and final dispatch; its progress flag is not a fence. Native verified backup IPC acknowledges its own file write                                     | Finish accepted import/native backup work. Read-only export does not mutate models but may produce an output file; it does not close profile stores                                                               |
| Background sync                            | Full sync, immediate upload and WebSocket download use `SyncCycleGuard`. `runWithSyncBlocked` fences/drains for destructive config changes, bumps sync epoch, and unblocks when its callback returns                                | Reuse the cycle admission authorities through a dedicated close flow; do not hold an operation lock while waiting for work that needs it. Do not reuse the destructive-config method unchanged as an update lease |
| Plugin buffers and independent credentials | Plugin coalescing timers and compression chains may precede dispatch; OAuth/secrets/sync credentials use separate IndexedDB promises                                                                                                | Flush already accepted buffered intent and await admitted credential writes; prevent new producer requests. Idle database connections themselves need closure, not export into JSON                               |
| Native settings and other profile files    | New simple-store lease covers only admitted store operations; native consent queue, backup writers, image/window-state writes and producer IPC remain outside it                                                                    | Drain accepted native commands where required. Chromium storage/cookie/preferences/LevelDB handles remain open until clean Electron termination                                                                   |

The concrete unclosed seam is **between accepted asynchronous commands and their
later storage/dispatch calls**. Freezing reducer mutations now could reject a
plugin commit or an archive command's final dispatch after the command already
started. Holding `OPERATION_LOG` while draining those commands could deadlock
them. Merely waiting for current counts to be zero does not prevent queued work
from entering later. Covering this seam requires coordinated admission/completion
handling at multiple producer boundaries, not a small change to capture or one
generic storage lock. That integration was stopped rather than returning a
misleading overall success result.

## Minimal Phase 3B.2 handoff contract (design, not implemented)

Prefer a dedicated, user-confirmed **clean-close preparation** followed by an
authoritative post-exit profile backup, rather than attempting to freeze every
Chromium file in the running app:

1. After consent, stop user/REST/plugin ingress and background cycle admission.
   Finish the intended before-close work (including any sync/finish-day work)
   before establishing the final boundary. Do not discard accepted commands.
2. Await accepted producer commands, flush plugin/time buffers, drain operation,
   archive, snapshot, credential and native-write acknowledgements. Use the normal
   lock order; never call the flush while holding its non-reentrant lock. Only
   then prepare the Phase 2 application-data checkpoint. It is supplemental
   recovery, not the full-profile backup.
3. Close native store admission after upstream producers are drained; require its
   returned lease to remain active. Overall preparation success needs **all**
   those authorities, not just this lease or checkpoint success. No overall
   success token exists in this revision.
4. Ask Electron to exit cleanly. In-memory queues must already be drained;
   IndexedDB connections, Chromium storage and utility-process handles remain
   active until exit. The existing two-second forced-exit fallback is not a clean
   completion acknowledgement and must not authorize an update backup/installer.
5. Before initiating close, the future helper must hold reliable OS process
   identities/handles covering the original Electron tree, and exclude reopening
   the **resolved** profile (including a custom `--user-data-dir`). A renderer
   callback, closed window, quit event or recycled numeric PID is insufficient.
   Raw copying may begin only after complete termination and released handles,
   with reopening excluded. No such mechanism is implemented here.
6. Cancellation or failed close prohibits copying/installing. While the original
   app is alive, release owned preparation leases, restore suspended producers
   and return control; never reset data. If a drain times out, accepted operations
   can still complete and must not be treated as cancelled. If the app crashes or
   is forcibly terminated, retain recovery data and report an unclean close;
   do not promote it to successful update preparation.

External-helper code can be developed separately against disposable closed
profiles, but **live assisted-install integration is not yet safe**. The next
application integration must close the producer-command seam above and rehearse
clean/failed close. No production signing authorization can substitute for it.
