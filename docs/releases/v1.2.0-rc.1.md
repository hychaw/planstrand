# Planstrand v1.2.0-rc.1

Windows x64 release candidate, prepared October 11, 2026 UTC. Publication and
production deployment are separate approval steps; neither is claimed here.

## Recurring Events and Weekly Templates

- Create timed or all-day recurring Events with daily, weekly or monthly rules,
  intervals, selected weekdays, explicit timezones and optional inclusive end dates.
- Edit this occurrence, this and future occurrences, or the entire series. Move,
  cancel and restore individual occurrences, with explicit exception handling.
- Create and edit Weekly Templates with multiple entries and date bounds; activate,
  deactivate and reactivate them without changing their identity. Calendar
  occurrences do not create permanent Event instances, Tasks or WorkSessions.

## Major fixes

- Preserve Task replay context through archived edits and strengthen semantic
  capability requirements across synchronization and retained history.
- Improve recurrence/template validation, narrow-screen wrapping, keyboard focus,
  accessible validation descriptions and dark-theme control contrast.
- Make feature-store registrations statically analyzable for production Angular AOT.

## Backup, recovery and compatibility

The RC1 recovery guarantee requires verified complete backup/snapshot restoration
and independent pre-upgrade copies. Encrypted operator operation-tail reconstruction
is limited to admitted histories; it is not guaranteed for every supported workflow
or historical format. Unsupported/ambiguous histories, incomplete ranges and missing
context remain fail-closed. An unsupported retained prefix can prevent CLI recovery
even with a later snapshot. A complete independently exported backup can instead
be imported directly. With no valid backup/current copy and refused history, some
or all data may be unrecoverable. Restoring an older backup loses subsequent edits.

Follow the [backup and restore rehearsal](../v1.2-backup-restore.md): export through
Settings → Sync & Backup → Import/Export, keep a checksummed copy outside the profile
and sync directory, preserve keys separately, import into a disconnected disposable
profile, compare persisted records and capability metadata, and restart to verify.
Rehearse real backups before upgrading their source profiles. Rotating local recovery
points and sync alone are insufficient independent backups. Operators must also
rehearse a consistent full database dump in an isolated database; see the
[server recovery runbook](../../packages/super-sync-server/docs/backup-and-recovery.md).

Compatibility package version remains `19.1.0`, operation schema remains **5**,
IndexedDB remains **12**, and the server package remains `1.0.0`. A V1.2 profile
cannot be opened by V1.1, even before Routines activation. Client rollback requires
a separate pre-upgrade V1.1 backup/profile; never open the upgraded profile in V1.1.
Non-English Routines strings currently use English fallback. Windows packages are
unsigned; execution remains subject to Windows and antivirus protections.

## Production deployment checklist (pending)

- [ ] Verify independent client backups, file-provider copies and a consistent full
      PostgreSQL dump, including accounts, operations, snapshots, sync-state capability
      floors and migration history. Rehearse restoration separately before cutover.
- [ ] Quiesce writes and pruning; retire old server instances before migration.
      Use the supported `scripts/deploy.sh` / `migrate-deploy.sh` procedure (startup
      migrations default off). Apply and verify
      `20261010050000_durable_semantic_requirements`, including the backfilled
      `user_sync_state.required_capabilities` floors, before admitting V1.2 writers.
- [ ] Start the enforcing server/shared-schema on every instance. Verify live
      `capabilities.operationSync` includes `ROUTINES_V1`, `TASK_REPLAY_CONTEXT_V1`
      and `ARCHIVE_COMMAND_V1` (and preserves existing requirements such as
      `TASK_FOLDER_OWNERSHIP_V1`). Verify unaware readers/writers are rejected;
      then resume service and distribute V1.2 writers. Server version alone is no proof.
- [ ] Preserve capability floors across snapshots, compaction, pruning and restore.
      Never drop/clear floors or roll back to a server that ignores them. Migration
      backfill cannot reconstruct erased evidence. Account for post-backup writes
      before rollback; do not restore over a live database.
- [ ] Review final committed artifact provenance, checksums, Windows identity and
      smoke results before authorizing any tag, workflow dispatch or publication.
