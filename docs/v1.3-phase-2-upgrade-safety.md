# V1.3 Phase 2: upgrade safety foundation

Completed on `feature/v1.3-balanced`, starting from
`712248de055091849abcc1e8f9c42a638ab7ea4c`. The comparison release is
`v1.2.0-rc.1` (`1a94b8c`). This milestone implements no installer or download
service and changes no historical release, tag, or asset.

## Implemented guarantees

Previously, the Electron `BACKUP` invoke handler caught serialization/write
errors and returned normally. Awaiting it could therefore acknowledge a failed
backup and let the routine backup service advance its success timestamp.

Routine writes now reject on failure. Successful invokes retain the existing
`Promise<void>` contract. Automatic consumers already catch failed attempts and
keep their subscription alive; their existing interval, overlap gate, empty-state
guard, and retention policy are unchanged. Retention runs only after a verified
write and remains best-effort; a retention-cleanup failure does not invalidate
an otherwise successful backup.

The shared writer serializes valid JSON, exclusively creates a temporary file in
the destination directory, writes and `fsync`s it, closes it, compares readback
with the serialized bytes, renames it, and compares the published file again.
Timestamp-plus-UUID names prevent normal successive writes from overwriting
each other. Only this attempt's temporary/unverified file is eligible for failure
cleanup. Existing valid files are never replaced to prepare a checkpoint.
Errors expose a fixed operation stage and a sanitized system error code, never
the original error message/cause or backup contents. A failed cleanup can leave
an orphan file; that does not turn a failed attempt into success. These checks
establish successful file persistence/readback, not immunity to subsequent disk
loss, deletion, or every possible power failure.

`UpgradeCheckpointService.prepare()` is the reusable renderer entry point. It:

1. Flushes the existing task-time accumulator.
2. Uses `OperationWriteFlushService.flushThenRunExclusive()` to drain captured
   writes, acquire the existing operation-log lock, and recheck the cutoff.
3. Refuses active hydration, fallback hydration, sync windows, unrecovered write
   failures, and undrained deferred actions.
4. Uses the existing archive-inclusive complete export. The snapshot service
   captures immutable reducer references synchronously before archive I/O; the
   lock keeps durable archive mutations outside that cutoff.
5. Validates models, relationships, and both archives without repair, then
   detaches the captured JSON before releasing the lock.
6. Awaits the verified native write and returns either
   `{ ok: true, path, coverage: 'application-data' }` or
   `{ ok: false, reason }`. Reasons are `UNAVAILABLE`, `PREPARATION_FAILED`, and
   `WRITE_FAILED`. Every failure must stop future installer progression.

Preparation never imports, resets, or repairs the live profile. The initial flush
performs ordinary persistence of pending edits. The boundary captures a point in
time; it does not permanently block later edits or sync.

## Exact checkpoint coverage

Checkpoints contain the existing `CompleteBackup` JSON envelope: timestamps,
cross-model version, required entity types/capabilities, and the supported
application model slices:

- Tasks, Projects, Folders, Tags, Planning placements, legacy Planner state,
  Sections, WorkSessions, standalone Events.
- Event series, occurrence exceptions (including moved/cancelled occurrences),
  Weekly Templates, recurring-task configuration, and retained capability floors.
- Both young and old Task archives and their archived time tracking, plus current
  time tracking, Notes, global configuration, reminders, Boards, metrics, simple
  counters, issue-provider models, plugin metadata and plugin user data.

Existing export normalization applies: the current Task is cleared, and production
snapshots clear the selected Task. Existing archive read normalization is reused.
This is recovery of supported application models, not a byte-for-byte store copy.

Files are plain JSON in `app.getPath('userData')/upgrade-checkpoints/` and retain
the existing export's sensitive configuration content. Treat them as private
backups. They are outside `backups/`, outside routine listing/rotation, and outside
the IndexedDB import recovery ring. No checkpoint pruning or latest-file pointer
is introduced; callers receive the exact verified path. The existing guarded
backup reader accepts this root for the normal complete-backup import path.

The export does **not** include every Electron profile file, all localStorage or
device-local settings/drafts, the separate `sup-sync` credential database, cookies,
client identity/vector clocks, the operation-log history/recovery ring, or
externally held encryption keys. Import uses the existing replacement semantics,
including a new client identity. This milestone implements neither complete
profile restoration nor automatic rollback. Keeping a checkpoint on the same
disk is not an independent disaster-recovery copy.

## V1.2 compatibility

The release and starting feature revision have identical relevant persistence
contracts: `SUP_OPS` IndexedDB **12**, operation schema **5**, cross-model **4.5**.
The database/model version constants, snapshot selectors, and Electron profile
identity match the release and remain unchanged. The feature branch can open a
supported V1.2 profile without a V1.3 migration. The default profile remains
`app.getPath('appData')/Planstrand`; `--user-data-dir=` continues to override it
before backup paths are resolved.

Tests reopen a version-12 database through the operation-log, archive, and client
identity readers and compare all store records and schema metadata. Existing
historical fixtures and V1.1 downgrade/future-database rejection tests are reused.
Checkpoint capture/import also exercises V1.2 series, a cancelled occurrence,
inactive Weekly Templates, and both archives through real export/import code and
isolated IndexedDB. Existing snapshot and import suites cover other model slices.

Future complete-backup cross-model versions are refused before repair/replacement.
Future local snapshot/operation schema stamps are refused before replay or
full-state shortcuts, bypassing destructive recovery. Migration cannot relabel a
future snapshot as current. Existing capability requirements, malformed historical
operation handling, and IndexedDB downgrade barriers are retained. No migration
is added solely for the product version.

## Required Phase 3 handoff and limits

A full filesystem profile checkpoint requires shutdown. Do not copy live Chromium
IndexedDB/LevelDB files. Phase 3 must:

1. Quiesce editing, tracking and synchronization, prepare the verified model export,
   and keep the application quiesced through exit. Abort on preparation failure.
2. Hand an external helper the resolved profile path, verified export path, process
   identity and an independent destination outside that profile. Do not infer the
   profile from the executable/install location; account for profile overrides and
   any supported Windows Store virtualization separately.
3. Exit the entire Electron process tree. The helper must wait for full process
   termination and released database handles before copying the closed profile.
4. Copy and verify the complete profile at the independent destination before
   starting installation. Preserve earlier verified copies until the new copy has
   been verified. Preserve external keys separately; OS-bound credentials may
   require the original Windows account/device or reauthentication.
5. Keep the same resolved profile path through installation/relaunch, then rehearse
   packaged V1.2-to-V1.3 upgrade and recovery using disposable profiles. Specify and
   verify failure/recovery behavior before claiming safe assisted installation.

There is no Phase 2 implementation blocker. Full-profile capture/restoration,
shutdown orchestration, installer integration, and a packaged recovery rehearsal
remain prerequisites for Phase 3 safety claims.
