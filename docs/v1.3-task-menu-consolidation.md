# V1.3 Task menu consolidation

This change is separate from the reminder delivery fix (`c14f31b`).

## Behavior and access audit

The Task context menu now contains Move up, Move down and Move Task to Folder.
Its duplicate planning icon strip is removed. The three-dot planning menu contains
planning destinations, Unplan and Schedule WorkSession. Its reorder and folder
movement buttons are removed. Opening either menu dismisses the other, including
menus on different rows.

Main rows retain right click, the Menu key / Shift+F10, and swipe-left access.
Touch rows also have a separate, labelled Task context menu button with a
44-pixel target and a distinct icon. Planning stays on the existing native details
summary, with Enter/Space, Tab and Escape behavior. Nested children previously
depended on the context menu's planning icons; they now receive the same shared
three-dot planning control. Existing Task detail panel schedule editing, selection,
completion swipes and other editor access remain available. Legacy planner and
calendar contexts retain their existing detail-panel access.

Keyboard Enter inside a planning control or Material menu now belongs to that
control rather than the Task title shortcut. Keyboard opening preserves the menu's
focus. A closing menu cannot steal focus from a newly opened menu. Obsolete
Move to Top/Bottom bindings are no longer shown in Settings or executed, and old
saved bindings no longer reserve a combo; their compatibility fields remain intact.

## Ordering

`TASK_ROW_MENU_ACTIONS` binds context-menu and row keyboard actions to their owning
`PlanstrandTaskListComponent`. Main rows emit the same `reordered` output formerly
used by the three-dot controls. Existing page handlers continue to use
`PlanstrandService.reorderTask` for canonical lists and the existing placement
commands for planning lists. No second persistence or reordering engine is added.

Canonical movement checks list edges, Project/backlog domains and Folder ownership.
Planning movement retains its current destination and placement order. Nested
movement uses the existing `TaskService.move` drag command with the same parent
as source and target. First/last children cannot move their parent or cross hierarchy
boundaries. Nested presentation is explicit so a child also displayed as a planned
main row cannot accidentally use that separate row's order. Completed/disabled
lists do not expose active reorder actions. Drag handles and existing drop handlers
are preserved.

## Focused validation

- **183 Jasmine tests pass** across six focused files covering menu commands, list/domain/hierarchy boundaries,
  stored-state ordering, existing planning commands, shortcuts and keyboard focus.
- Five focused Playwright tests pass: menu separation/mutual dismissal/keyboard,
  Folder movement and child ordering after reload, touch access, and canonical /
  day / week ordering with drag-and-drop and persistence in Light and Dark themes.
  The single touch test also passes after the final icon distinction; its 390px
  screenshot was visually inspected.
- Targeted ESLint, formatting and diff checks pass. The Angular development server
  compiles the changed components and templates.

Existing Folder-movement browser tests were updated to use the relocated action;
their unrelated flows were not run. No schema, sync contract, executable, installer,
release, push or system security changes were made. Original untracked files and
previous candidate/profile directories remain intact.

Manual check: create two Tasks in a disposable development profile. Right-click
the second and use Move up; verify the first row's Move up is disabled. Open its
three-dot menu and confirm only planning/scheduling actions appear; switch between
the menus. Repeat using Shift+F10 and a touch Task-menu button, then reload and
check order. Add two children and verify their moves stay among siblings and their
three-dot planning controls remain accessible.
