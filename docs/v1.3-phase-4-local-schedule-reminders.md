# V1.3 Phase 4: local Event and WorkSession reminders

## Product behavior

Timed standalone Events have a Reminder selector in the existing editor. WorkSessions
have a Reminder submenu in their existing Calendar menu. Existing translated options
are reused: Never (Off), when it starts, or 5, 10, 15, 30 or 60 minutes before it starts.
The default is Off. No Task, Event or WorkSession is created by setting a reminder.
The WorkSession submenu exposes radio selection state to assistive technology and
uses the existing Material menu keyboard behavior. The Event selector uses the
existing Blue Thread native control styling in light/dark and narrow layouts.

## Local storage and compatibility

`LocalScheduleReminderService` stores preferences in profile-local `localStorage`
under the stable key `planstrand_local_schedule_reminders_v1`. Keys are namespaced
by entity kind and identity (`event:<id>` / `workSession:<id>`), with an optional
minute offset and consumed reminder instants. The storage key is independent of
the application/release version and survives normal restart and in-place upgrade
using the same profile. Recent consumed instants are retained across Off/On;
older history is trimmed when a new instant is consumed.

These preferences are **not included in model-only JSON backup exports**, are not
synced, and do not move with an exported model to another device/profile. Clearing
application site/profile storage removes them. Importing an entity with a different
identity does not inherit the old entity's preference. Missing entity preferences
are retained but inert, so partial hydration/import cannot accidentally discard
preferences. No shared entity fields, operation payloads, sync capabilities,
schema migrations or database version changes are involved. Existing V1.2 model
data requires no new migration.

## Scheduling and lifecycle

The existing reminder worker supplies a 10-second tick; there is no second worker,
timer loop, native scheduler or pre-scheduled Event/WorkSession OS alarm. Delivery
waits for initial data hydration and pauses during imports and when the existing
Disable all reminders setting is enabled. Each tick derives the instant from the
current hydrated entity start minus its local offset. WorkSession titles come from
their current Task. Deleted entities, missing Tasks, completed WorkSessions and
all-day Events cannot deliver. Recurring Event occurrences and Weekly Templates
are not consulted. Standalone Events have no separate cancellation state: removing
the Event cancels its reminder.

Movement automatically changes the derived instant without rewriting the local
preference. A new instant is eligible, while an already consumed instant is not.
Completing a WorkSession suppresses delivery; reopening it preserves the offset
but does not replay a consumed instant. Saving an Event as all-day in the editor
turns its preference Off; all-day conversion through other model paths makes any
retained preference inert while the Event is all-day. The delivery guard rechecks
identity, current instant, title, completion, eligibility, import state and global
disabling after asynchronous desktop notification permission/registration waits.

The overdue grace is **two minutes**, inclusive, on every tick including startup
and resume. Older overdue instants are consumed silently; they do not flood the
user with historical notifications. Browser/OS throttling can delay a tick. Reminders
missed by more than the grace period are deliberately not replayed.

## Delivery limitations

Delivery uses the existing desktop notification service while the application is
running. The OS/browser must permit notifications. This phase does not provide
native mobile/background alarms or notifications while the entire app is closed.
Narrow-screen controls remain usable independently of desktop notification support.

Consumption is persisted **before** requesting notification delivery. This gives
at-most-once attempts across normal restart/resume, rather than pretending the
application can confirm that the user saw an OS notification. A denied permission,
OS suppression, a crash after consumption, or a stale schedule detected during a
permission wait can therefore result in no visible notification for that instant.
A legitimate reschedule to a new instant remains eligible. Failed local storage
writes prevent delivery and are logged, so a delivery with no durable deduplication
record cannot repeat on restart. The existing application single-instance/profile
behavior applies; no new cross-window locking protocol was added.

## Validation

Focused Jasmine coverage exercises local setting/disabling, restart persistence,
all offsets, hydration/import/disabled gates, Event and WorkSession movement and
deletion, completion, all-day conversion, worker tick routing, repeated ticks,
startup/resume deduplication, overdue grace, storage failure, stale permission
waits and unchanged shared Task operations. Browser coverage exercises Event
selection/reload/keyboard access, both themes at 390/320px, all-day conversion,
and WorkSession menu selection/reload/disabling.

Final focused validation on 2026-10-13:

- 144 Jasmine tests passed: reminder service/module/migration, local schedule
  reminders, notification service, Event Calendar/editor, WorkSession Calendar
  edits/component, and existing Task reminder effects.
- Both focused Playwright tests passed with installed Chrome. An ignored local
  configuration selected Chrome because the bundled Playwright Chromium was absent.
- Targeted ESLint, Prettier checks and `git diff --check` passed for changed files.
- The development server compiled the Angular application and templates successfully.
  No production build or broad test suite was run.

The four untracked V1.2 reports and the untracked Phase 3B.2 investigation report
and PowerShell probe are outside this change. No native probe was run. Installer,
historical release, checkpoint and authenticated-download behavior is untouched.
