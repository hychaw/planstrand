# V1.3 Phase 5C.2A: Calendar weeks and ordering

## Behavior and supported boundaries

Calendar Week now starts at the configured weekday and navigation moves by complete
civil weeks. The common calendarWeekStart utility also supplies Planning week keys.
Calendar continues to resolve Today in its display timezone; Day remains selected-date
based and Month/Year keep their existing calculations. Event/WorkSession timestamps
are never written by these gestures. Week numbers use the configured weekday too.

Tasks, Inbox and Folder views previously enumerated Task entities, ignoring persisted
Project taskIds/backlogTaskIds. Same-Folder drops called the ownership command and
ignored the index. These views now project the existing Project order and dispatch
existing persistent anchor-based reorder actions. Parent rows retain their subTaskIds;
subtasks are not promoted, reparented or duplicated by outer-list reordering.

Unplanned uses the same canonical order across Folders: Project.ids order, then each
Project's regular list followed by its backlog list, filtered to unplanned root Tasks.
Different Folders can interleave within one Project list. Adjacent movement can cross
Folder boundaries in Unplanned without changing ownership. Movement across Projects
or regular/backlog boundaries is unsupported and disabled/rejected. Tasks missing an
authoritative Project list remain visible but cannot be manually reordered here.
No new global ordering schema or fake Planning placements were introduced.

Focus, This Week's week-level section and each day section use existing absolute
Planning placement operations. Move up/down are labelled actions in the compact row
menu; endpoints are disabled. Focus translates its filtered position into the full
Planning list so completed Tasks do not change the intended adjacent visible move.
Dragging between planning destinations and into Calendar retains existing behavior.
Cross-Folder drops retain the existing ownership command; their drop index is not a
promise of arbitrary cross-Project ordering.

## Phase 5C.2B handoff: multiple placements

Independent placements for one Task are **not representable by PLANNING_V1**.
`packages/shared-schema/src/planning.ts` keys a single revisioned register by Task ID;
its placement contains exactly one DAY/WEEK target and orderKey. Null is that Task's
unplanning tombstone. The reducer merges one register per Task. Selectors, status
and commands likewise assume placement ID equals Task ID.

Capture (`operation-log.effects.ts`) uses the record's revision identity; replay
(`operation-converter.util.ts`) validates record.id against operation.entityId and
validates the strict V1 record shape. File-sync compatibility explicitly requires
PLANNING_V1. The v4-to-v5 projection deliberately collapses duplicate legacy Task
memberships into one placement. Encoding placement IDs as pretend Task IDs or adding
extra V1 fields would violate these contracts and selectors' live-Task checks.

A shared schema **and capability change is unavoidable**. Smallest safe path:

1. Introduce a distinct Planning capability/operation family with stable placement
   identity plus explicit taskId; each placement has its own target, order and
   revision/tombstone. Specify whether duplicate destinations are allowed and what
   “Unplan Task” means before implementing commands.
2. Deterministically migrate each live V1 register to one V2 placement, preserving
   target/order/revision evidence, and retain V1 tombstones/cutover evidence so old
   operation replay cannot resurrect or overwrite V2 placements. Keep the existing
   V1.2-to-V1 projection intact, then migrate its result once. Do not reinterpret
   historical PLANNING_V1 operations as a multi-placement command.
3. Gate file sync, snapshots/imports and server replay on the new capability before
   accepting V2 data. Older clients must refuse unsupported data rather than flatten
   it. Update selectors, task deletion cleanup and operation replay tests together;
   include offline upgrades, mixed-client refusal and deterministic migration tests.

Phase 5C.2A keeps IndexedDB 12, operation schema 5 and cross-model 4.5 unchanged.
The exact next version/cutover depends on the chosen V2 persistence representation;
capability gating alone is insufficient if older snapshot validators can accept and
silently drop the new state. No V2 schema or migration is implemented here.
