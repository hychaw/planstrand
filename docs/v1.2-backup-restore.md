# V1.2 independent backup and restore before upgrading

Complete this rehearsal before upgrading real data. Keep sync disconnected in
the rehearsal profiles: importing while connected can replace other devices.
Use the existing supported UI; no operation-tail recovery is needed.

1. In the current client, open **Settings → Sync & Backup → Import/Export**
   and export the complete backup to a file. Preserve the V1.1 export before
   opening that profile with V1.2. Copy the export to separate protected storage,
   outside the application profile and sync-provider directory. Record date,
   client/source revision and SHA-256 (`Get-FileHash -Algorithm SHA256 <file>`).
   Preserve encryption keys separately and confirm they are available.
2. Close the source client. Launch the candidate Windows executable with a new
   disposable profile, for example:

   ```powershell
   & '<candidate>\Planstrand.exe' "--user-data-dir=$PWD\.tmp\v1.2-restore-rehearsal"
   ```

   Choose an unused profile path. Confirm the profile is empty; do not configure
   sync. Open the same Import/Export section, choose **Import from File**, select
   the copied backup and accept the replacement confirmation.

3. Check Task identities/Folder ownership, Today/This Week placement, WorkSession
   links, standalone Events, archives, Notes and settings relevant to your data.
   For a V1.2 backup also check recurring series, moved/cancelled occurrences and
   weekly templates, including inactive entries. Export again and compare persisted
   records and required capability metadata; counts alone are insufficient.
4. Close the entire process and reopen the same disposable profile. Recheck the
   records and Calendar occurrences. Retain the original backup and checksum
   until the upgrade and a fresh independent post-upgrade backup are verified.
   If import or validation fails, stop the upgrade and preserve all copies.

A V1.2 profile uses IndexedDB schema 12 and cannot be opened by V1.1, even before
Routines activation. Rollback uses a separate pre-upgrade V1.1 backup/profile;
never point V1.1 at the upgraded profile. A restore returns to the backup's point
in time: later edits may be lost. Local recovery points rotate and can disappear
with device/profile loss; sync can replicate an accidental overwrite.

For operators, also preserve file-provider data and take a consistent full
PostgreSQL dump including accounts, operations, snapshots, sync-state capability
floors and migration history. Restore that dump into a separate disposable
database with the matching application/schema revision and verify representative
accounts before cutover. A gzip header/size check is not a restore rehearsal.
Use the [server runbook](../packages/super-sync-server/docs/backup-and-recovery.md)
for commands with your actual container/role/database names. Accounts-only dumps
cannot recover user content without a verified complete client. Keep production
writes/pruning quiesced for cutover and account for writes after the backup;
do not restore over a live database or clear floors to enable old clients.

Existing executed upgrade/restore evidence is recorded in
[Phase 5b.2](routines-phase-5b2.md) and the current targeted native result in
[final readiness](routines-rc1-final-readiness.md). This procedure does not claim
that any particular user's backup or production database has been rehearsed.
